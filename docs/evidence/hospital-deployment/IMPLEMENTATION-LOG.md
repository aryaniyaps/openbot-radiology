# Hospital deployment implementation record

The requested outcome is a separate IT management server, a doctor client, and sample HMS/PACS cases with a verified physician journey. The existing native OpenMausBot execution host and KVM hospital remain authoritative; no inference backend fork or hospital replacement was introduced.

- Provisioned separate `kauvery-it` KVM guest at `192.168.178.11`, 2 vCPUs, 2 GiB RAM, 10 GiB virtual disk. The hospital remains `192.168.178.10`. Both guests autostart.
- First cloud-init user creation failed because Ubuntu already has an `operator` group. Inspected the actual guest cloud-init error through the guest agent; created the scoped operator user with the existing primary group and installed the generated public key and sudo rule. SSH and native nginx readiness passed afterward. The provisioning source now specifies the primary group explicitly. Initial cloud-init error remains historical evidence; it is not presented as a clean first bootstrap.
- Established a dedicated host SSH account whose key permits only forwarding to the two native loopback endpoints. Doctor and IT gateway traffic traverse this encrypted tunnel. The IT guest exposes trusted TLS doctor and administrator origins with separate credentials; raw native and monitoring ports bind guest loopback.
- Native `admin` scope alone cannot read client workspace APIs. The actual 403 named the missing `client` scope. Replaced that new IT session with `admin` plus `client`; revoked the unused admin-only session. Doctor session retains only `client`.
- Moved the doctor proxy from a user service tied to the checkout to a root-managed system service under the nonprivileged `radiology-gateway` account and stable `/opt/radiology-client` paths. Native execution host and history remain intact. Doctor proxy validates the public origin before translating it for native same-origin checks. Execution settings, permanent permissions and configuration remain IT controlled, including normalized dot-path checks.
- Operational monitoring polls native role availability, HMS and PACS, stores only operational samples in SQLite for 30 days, and exposes an authenticated status page, history chart and Prometheus text metrics. Patient messages, prompts, image bytes and case titles are excluded.
- First practice order used OpenMRS `TestOrder`, while this Bahmni radiology integration uses `org.openmrs.Order`. Native encounter results excluded the test order and no MWL arrived. Voided only that unused owned practice order (`ORD-21`, with no images or report) and retained the reason privately. Created generic radiology order `ORD-22` and used Bahmni's native encounter save so the integration receives the encounter event.
- Scanner replay then reached native C-FIND but the old SCP invocation failed at its separate transport policy. Changed the existing acquisition owner to stream owned DICOM files over the pinned SSH channel. No source pixels, geometry or class UIDs are changed. All five fresh practice cases subsequently passed native worklist lookup, C-STORE and archive instance-count checks: DX 1, CT 241, MR 95, US 1 multiframe object, MG 4.
- Deployed doctor worklist with modality and identifier filters, verified identity-preserving native chart/viewer/report links, and one-click creation of a separate native assistant case thread. The client does not save hospital records on the doctor's behalf.
- Sixteen live HTTPS authorization/monitoring checks passed. Anonymous doctor access is denied, doctor IT/config/session/SOUL/permanent permission/execution mutations are denied, cross-origin writes are denied, IT has native management access, and monitoring reports all three services available. Valid case thread creation remains available. The owned verification thread was removed after testing.
